SCCM Software Collection Consolidation - Operational Documentation

Document purpose: technical and operational documentation for Confluence.

What this script does:
Consolidates versioned SCCM software collections into three master collections, optionally builds application supersedence, migrates deployments to the latest app version, safely removes legacy objects, and cleans up empty folders.

1. Scope and Outcomes

The script performs software-family consolidation under SCCM by creating or reusing these master collections:

  • <Canonical> - Install (Available)
  • <Canonical> - Install (Required)
  • <Canonical> - Uninstall

It places masters in:

<SiteCode>:\DeviceCollection\Application Deployment\<TargetFolder>

Then it computes membership and deployment intent from legacy collections, migrates deployments to latest version, preserves app versions needed by task sequences, and deletes obsolete collections/apps/deployments in dependency-safe order.

4. Deep Dive by Workflow Area

4.1 Collection Classification and Membership Math

The script classifies collections into legacy buckets and computes target memberships using set operations:

  • Legacy Available: name contains Install (Available)
  • Legacy Required: name contains Install, excluding Available and Uninstall
  • Legacy Uninstall: name contains Uninstall

Membership model:

  • Master Available = union of Legacy Available members
  • Master Required = union of Legacy Required minus Master Available
  • Master Uninstall = union of Legacy Uninstall members

This avoids placing a device in both Available and Required for the same install intent.

4.2 Deployable Application Selection

The script first looks for an exact canonical-name app. If none exists, it selects the latest versioned app for that software family and logs the fallback decision.

4.3 Supersedence Behavior

  • Skipped if ManageSupersedence is not specified.
  • Builds normalized versioned app list and sorts oldest -> newest.
  • Links adjacent pairs only (linear chain).
  • Uses parameter-set fallbacks to support environment differences in Set-CMApplicationSupersedence.
  • Logs success/failure per link without hard-failing the full run for one failed link.

4.4 Cleanup Plan Logic

Cleanup is enabled only when DeleteOldCollections is specified. Then:

  1. Identify non-master collections.
  2. Build deployment delete candidate set from those collections.
  3. Compute app keep set: two newest versions + task-sequence-referenced versions.
  4. Classify old app versions for deletion.
  5. Sort legacy collections by version descending (newest first) to reduce include-rule conflicts.
  6. Prompt for confirmation unless AutoApprove is set.
  7. Migrate per-collection deployments to latest app, then delete old deployment objects.
  8. Delete old apps (skip if referenced by task sequences).
  9. Reset caches, then delete old collections.
  10. Delete empty folders under Application Deployment (preserving target folder).

4.5 Retry Strategy

Failed app/deployment/collection deletes are collected in in-memory lists. Retry rounds then:

  • Reset runtime caches between rounds.
  • Retry object removals up to RetryCount.
  • Sleep RetryDelaySeconds between rounds.
  • Log progress and final retry completion.

5. Why the Script Is Structured This Way

5.1 Migration Before Deletion

Deployments are migrated to the latest app before deleting legacy deployments and collections. This preserves delivery continuity and avoids accidental deployment gaps.

5.2 Keep Set Includes Task Sequence References

Even old versions are preserved when referenced by task sequences, preventing operational breakage in TS steps that still point to older application identifiers.

5.3 Cache Resets at Mutation Boundaries

SCCM mutations (supersedence, deletes) can invalidate previously fetched provider objects. Cache reset points force fresh reads to reduce stale-object failures and inconsistent behavior.

5.4 Dependency-Safe Collection Deletion

Collection dependency handling plus sorted deletion order minimizes include/exclude and limiting-collection conflict failures during cleanup.

6. Safety, Idempotency, and Failure Controls

Control Implementation Benefit
Scope validation Rejects too-short software names in sensitive phases. Reduces risk of broad unintended impact.
Dry run mode Uses dry-run wrappers and log-only behavior. Safe preview before production mutation.
Auto approval control Interactive prompt unless AutoApprove is set. Operator confirmation gate for destructive actions.
Robust deployment removal Fallback attempts by InputObject, fresh fetch by ID, and direct ID/name parameter sets. Avoids interactive prompts and stale-object failures.
Null-safe object handling Property alias resolution and guard checks before property access. Prevents null-reference crashes on irregular SCCM objects.
Retry mechanism Tracks failures and retries with delay. Improves success in transient provider conditions.
Structured stage logging Tracks current stage and logs stage-specific failure context. Faster troubleshooting and reproducibility.
Important behavior note:
Supersedence operations can create new app revisions. A cache reset is intentionally performed before cleanup so subsequent app and deployment queries use fresh objects.

7. Outputs and Audit Artifacts

  • Console logs with timestamped INFO/WARN/ERROR/SUCCESS/DEBUG levels.
  • End-of-run summary counts (collections processed, migrations, failed objects).
  • CSV exports under C:\Temp\SCCMCleanupResults, including deployment migration audit.

8. Runbook Guidance

8.1 Recommended execution sequence

  1. Run once with -DryRun and inspect plan/log output.
  2. Run with -ManageSupersedence and -DeleteOldCollections.
  3. Use -AutoApprove only in controlled automation or when plan has been reviewed.
  4. If diagnostics are needed, rerun with -EnableDebugLog and capture full output.

8.2 Example command

C:\Path\To\SCCMSoftwareCollectionConsolidation.ps1 \
  -SiteCode P03 \
  -SoftwareName "Example Product" \
  -TargetFolder "Example Product" \
  -ManageSupersedence \
  -DeleteOldCollections \
  -AutoApprove

9. Known Behaviors and Notes

  • If multiple software-family names are detected and AutoApprove is not set, the script prompts for selection.
  • When no legacy Available collections exist, master Available may be created and deployed empty by design.
  • Application deletions are skipped if task sequence references are present.
  • Folder cleanup uses SCCM and WMI discovery to identify empty candidates under Application Deployment.
  • The script is designed for reruns and no-op states; repeated execution should converge on the same master-state model.
